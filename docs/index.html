The problem

Coding agents are fast and agreeable. Left alone they write the production code before the test, fold a rename into a bug fix, and report that it all went well.

None of that shows up in review, because the diff looks fine. What is missing is the order things happened in — and a diff cannot show you order.

The idea, in one table

Two kinds of change exist, and they must never share a commit.

KindWhat it doesHow you check it
StructuralMoves code around. Renames, extracts, reorders.Tests pass before and after, unchanged.
BehaviouralChanges what the program does.A test that failed now passes.

Mixing them is what makes a diff unreviewable. A reviewer cannot tell whether the 200 moved lines are the same 200 lines, so they skim — and the one changed line goes through. Separating them is the whole trick, and it is Kent Beck's, not ours.

Pro

The free core is advice the agent reads. Pro checks whether the advice was followed, and helps in the two places the free core leaves you stuck.

Point it at a repo you already have

  RED      13   GREEN  99   STRUCTURAL  10
  MIXED     5   UNPROTECT 42   TEST-CUT 20

Problem rate: 35%  (67 of 189)

It works on repositories that never used this tool, which is what makes it useful on day one. Ten seconds, no setup, and it will tell you something true.

RED — a test written before the code.
GREEN — production and test changed together.
STRUCTURAL — code moved, behaviour unchanged.
UNPROTECT — behaviour changed, no test in the commit.
MIXED — code moved and changed at once. Unreviewable.
TEST-CUT — tests shrank while production code changed.

Questions

Does this only work with Claude Code?

The skills are written for Claude Code. The command-line tools — rgc-drift, rgc-audit, rgc-report — are plain Python and git, and work anywhere, with or without an agent.

What does it need installed?

Python 3 and git. Nothing else — no packages, no services, no account.

Does my code leave my machine?

No. Everything runs locally against your own git history. There is no server, no telemetry, and no network call.

Will it prove that skipping tests causes defects?

It will tell you whether that is true in your repository, which is a different and more useful thing. The Team report traces fix commits back to whatever introduced the lines they changed, then compares. Sometimes the link is strong. Sometimes there is no link at all, and the report says so plainly rather than explaining it away.
